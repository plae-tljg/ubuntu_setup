### ASSISTANT
To make PostgreSQL accessible from other machines on the same network in your Ubuntu VM, you need to configure **two key files**:

---

### ✅ 1. Edit `postgresql.conf` — Listen on all interfaces

Locate the config (usually in `/etc/postgresql/<version>/main/postgresql.conf`):

```bash
sudo nano /etc/postgresql/*/main/postgresql.conf
```

Find and modify the `listen_addresses` line:

```conf
listen_addresses = '*'   # or '0.0.0.0' for IPv4 only
```

> 💡 Ensure it's not commented out (`#` removed).  
> If `listen_addresses` doesn’t exist, add it under **CONNECTIONS AND AUTHENTICATION**.

---

### ✅ 2. Edit `pg_hba.conf` — Allow network connections

Edit the client authentication config:

```bash
sudo nano /etc/postgresql/*/main/pg_hba.conf
```

Add a line like this **at the end** (or before stricter rules) to allow connections from your subnet, e.g., `192.168.13.0/24`:

```conf
# TYPE  DATABASE        USER            ADDRESS                 METHOD
host    all             all             192.168.13.0/24         md5
```

> 🔍 Replace `192.168.13.0/24` with your actual network (e.g., `192.168.1.0/24`).  
> `md5` enables password auth (recommended). Use `trust` only for testing in secure LANs.

Optionally, if you want *any* private IP:

```conf
host    all             all             10.0.0.0/8              md5
host    all             all             172.16.0.0/12           md5
host    all             all             192.168.0.0/16          md5
```

⚠️ Avoid `0.0.0.0/0` unless you understand the security implications.

---

### ✅ 3. Ensure firewall allows port 5432

If `ufw` is active:

```bash
sudo ufw allow from 192.168.13.0/24 to any port 5432
# or more restrictively:
sudo ufw allow 5432/tcp
```

Check status:  
```bash
sudo ufw status verbose
```

Also verify your **VM network mode** (e.g., in VirtualBox: *Bridged* or *NAT with port forwarding*; in KVM/QEMU: *bridged via br0* or *macvtap*).  
Since you mentioned bridging (`br0`) and static IPs like `192.168.13.108`, your VM likely has a real LAN IP — good.

---

### ✅ 4. Restart PostgreSQL

```bash
sudo systemctl restart postgresql
```

Check it’s listening externally:

```bash
ss -tulnp | grep :5432
# Should show: 0.0.0.0:5432 or :::5432
```

---

### ✅ 5. Test connection from another machine

```bash
psql -h <your-vm-ip> -U <username> -d <dbname>
```

If you get `Connection refused`, check:
- Is `listen_addresses = '*'` applied? (restart required)
- Is `pg_hba.conf` rule matching the client IP?
- Is VM firewall / host firewall (e.g., Windows Defender) blocking 5432?
- Is the VM really reachable? Try `ping` and `telnet <vm-ip> 5432`.

### 🔹 1. **How to "even allow" (i.e. allow *any* IP) — and whether you should**

You *can* configure PostgreSQL to accept connections from **any IP address**:

#### ✅ In `pg_hba.conf`:
```conf
host    all    all    0.0.0.0/0    md5
```
- This allows **all IPv4 addresses**.
- For IPv6 too:
  ```conf
  host    all    all    ::0/0        md5
  ```

⚠️ **But this is strongly discouraged unless absolutely necessary**, because:
- It exposes your DB to the entire internet if the VM is reachable externally.
- Even on a trusted LAN, it’s better to restrict to your subnet (e.g. `192.168.13.0/24`).

✅ **Safer alternatives**:
- Allow only your company subnet: `192.168.13.0/24`
- Allow only specific IPs (e.g. dev machines):
  ```conf
  host    all    all    192.168.13.108/32    md5
  host    all    all    192.168.13.114/32    md5
  ```

> 🔐 Remember: `pg_hba.conf` controls **who can attempt to log in** — the actual login still requires a valid PostgreSQL user + password (if using `md5` or `scram-sha-256`).

---

### 🔹 2. **What do `/24`, `/32`, etc. mean? → CIDR Notation**

It’s **CIDR (Classless Inter-Domain Routing)** notation: `IP_ADDRESS/PREFIX_LENGTH`

| Notation        | Meaning | Example Range (for `192.168.13.x`) |
|----------------|---------|-------------------------------------|
| `192.168.13.0/24` | 24-bit network prefix → 32−24 = 8 bits for hosts → **256 IPs** (`.0` to `.255`) | `192.168.13.0` – `192.168.13.255` |
| `192.168.13.108/32` | 32-bit prefix → **exactly one IP** | only `192.168.13.108` |
| `192.168.0.0/16` | 16-bit prefix → 16 host bits → **65,536 IPs** | `192.168.0.0` – `192.168.255.255` |
| `10.0.0.0/8` | 8-bit prefix → 24 host bits → **16.7 million IPs** | `10.0.0.0` – `10.255.255.255` |

#### 💡 Quick reference for common subnets:
| Prefix | Hosts | Typical Use |
|-------|-------|-------------|
| `/32` | 1     | Single host (e.g., your VM at `192.168.13.108`) |
| `/30` | 4     | Point-to-point links |
| `/24` | 254 usable* | Standard home/company LAN segment |
| `/16` | 65,534 usable* | Larger private networks |

> \* `.0` is network address, `.255` is broadcast (not usable for hosts in `/24`), so **254 usable IPs**.

---

You’ll likely see something like:
```

```
→ So your VM is in `192.168.13.0/24`. That’s the safe range to allow.

### 🔍 Why this happens

PostgreSQL distinguishes **connection types**:
| Connection      | Method (by default in `pg_hba.conf`) | Auth Used |
|----------------|----------------------------------------|-----------|
| **Local UNIX socket**<br>(e.g. `psql -U postgres`) | `local` lines in `pg_hba.conf` | Usually `peer` or `ident` |
| **TCP/IP**<br>(e.g. `psql -U postgres -h localhost` or `-h 127.0.0.1`) | `host` lines | Usually `md5` (password) |

Your error:
```text
FATAL: Peer authentication failed for user "postgres"
```
→ You ran `psql -U postgres` → used **UNIX socket** → `peer` auth → PostgreSQL checked: *"Is the OS user (`fit`) named `postgres`?"* No → ❌

But `psql -U postgres -h localhost` → forces **TCP/IP** → uses `md5` → asks for password → ✅

### ASSISTANT
Inside `psql`, you can check the **current user** (role), **current database**, and other session info in several ways — here are the most useful and standard ones:

---

### ✅ 1. Quick one-liners (most common)

```sql
SELECT CURRENT_USER;
-- or
SELECT USER;
-- or (more explicit)
SELECT SESSION_USER;
```

| Command | Meaning |
|--------|---------|
| `CURRENT_USER` | Effective role (may differ if `SET ROLE` was used) |
| `USER` | Alias for `CURRENT_USER` |
| `SESSION_USER` | Original login role (never changes during session) |

💡 In 99% of cases, they’re the same unless you’ve done `SET ROLE`.

Example output:
```text
 current_user 
--------------
 postgres
(1 row)
```

---

### ✅ 2. Show full connection info at once

```sql
SELECT CURRENT_USER, CURRENT_DATABASE(), INET_SERVER_ADDR(), INET_CLIENT_ADDR();
```

Output:
```text
 current_user | current_database | inet_server_addr | inet_client_addr 
--------------+------------------+------------------+------------------
 postgres     | postgres         | 127.0.0.1        | 127.0.0.1
```

- `INET_SERVER_ADDR()` → IP PostgreSQL is bound to (server side)  
- `INET_CLIENT_ADDR()` → IP you connected *from* (client side)  
  - For local socket: may return `NULL`  
  - For TCP (`-h localhost`): `127.0.0.1`  
  - For remote: e.g. `192.168.13.114`

> 🔍 Tip: If `INET_CLIENT_ADDR()` is `NULL`, you’re using **UNIX socket** (local, `peer` auth).

---

### ✅ 3. Meta-command (psql internal)

```sql
\conninfo
```

Example output:
```text
You are connected to database "postgres" as user "postgres" via socket in "/var/run/postgresql" at port "5432".
```

- Shows user, DB, host (socket vs TCP), port  
- Very human-readable ✅

---

### ✅ 4. Check if you’re a superuser

```sql
SELECT rolsuper FROM pg_roles WHERE rolname = CURRENT_USER;
```

Returns `t` (true) or `f` (false).

Or simpler:
```sql
SHOW is_superuser;
```
→ Returns `on` or `off`

### 🔁 Bonus: Change role temporarily (for testing)

```sql
SET ROLE fit;          -- switch to role 'fit' (if member or allowed)
SELECT CURRENT_USER;   -- now shows 'fit'
RESET ROLE;            -- go back to original
```

(Only works if your current role has `SET ROLE` privilege on the target role.)
